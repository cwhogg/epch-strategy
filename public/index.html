Architecture brief · For a Claude Enterprise / Teams customer

Building a Company-Wide Claude Knowledge & Skill System

A practical plan for uploading decks, docs, and reusable workflows so Claude personalizes every output across the org — and so you, as the operator, can iterate on those workflows independently and push improvements seamlessly.

The shape of the answer

Modern Claude (Teams / Enterprise, May 2026) gives you four primitives to personalize Claude for an org. Combine them right, and the company gets context-aware outputs without anyone copy-pasting "remember our brand voice" into every chat.

Workflow

Skills

Procedural knowledge — how to do a thing. A folder with a SKILL.md + scripts + templates + brand assets. Auto-activates when Claude sees a relevant task.

Distribution

Plugins

A bundle of skills + connectors + sub-agents + slash commands shipped together. Distributed through a private GitHub marketplace your org subscribes to.

Live data

MCP servers / Connectors

Live data and actions — your CRM, data warehouse, Notion, internal APIs. Use when the data changes and you need fresh answers.

Context

Projects

Static, always-loaded context for an ongoing piece of work (a product launch, a client engagement). Different from skills — projects are scoped, skills are global.

Specialist

Sub-agents

Specialized review/critic personas (e.g. coo-reviewer, brand-checker) that a skill can invoke as a separate read-only pass.

One-paragraph plan

Stand up a single private GitHub repo that you own and operate. Inside it, define one plugin marketplace ("Acme Internal"). Inside that marketplace, ship one or more plugins (e.g. acme-foundation, acme-go-to-market). Each plugin bundles skills (pitch-deck, exec-memo, brand-guidelines, company-context), sub-agents (coo-reviewer, brand-checker), and any MCP servers (acme-data, acme-knowledge). The org's Claude admin subscribes once; updates flow from your git push to every employee's Claude.

Why this stack, not just Projects Projects are great for a specific ongoing piece of work, but they don't auto-trigger across all conversations and don't carry executable code or sub-agents. For company-wide "Claude always knows our brand / format / context," you want skills inside a plugin marketplace — that's the only mechanism that gives you (a) automatic invocation, (b) executable templates, (c) versioned distribution, and (d) admin-level rollout controls.

How it works

Every employee gets the foundation plugin automatically. On top of that, each person also receives the plugin for the team they're on — so an exec gets foundation + exec; a salesperson gets foundation + BD; an engineer gets foundation + engineering. Claude composes them, and the most specific layer wins where they conflict.

Reading the diagram

The foundation plugin is everyone's baseline. It carries the truly universal stuff: company principles, brand voice, positioning, the meeting-notes and weekly-update formats, plus the org-wide connectors (Slack, GDrive, Notion) that every employee benefits from.

Each team plugin layers role-specific skills, sub-agents, MCP servers, and connectors on top of foundation. An exec drafting a board update gets company-principles + exec-principles + the board-update skill + the coo-reviewer sub-agent + live numbers from acme-data — all without naming any of those things explicitly. A salesperson writing a proposal gets company-principles + bd-principles + client-proposal + pricing-reviewer + live deal context from Salesforce.

One person can belong to multiple groups. A founder-engineer who's also on the exec team gets all three layers (foundation + exec + engineering); group memberships compose additively.

Naming & org reality check The team boxes are illustrative. Your real groups might be Sales, Marketing, RevOps, Customer Success, Product, Design, Finance, People — split or combine them to match how the company already organizes itself in Slack channels and Notion spaces. The principle holds either way: one foundation plugin everyone gets, plus one plugin per real team.

Mental model

Skills vs Projects

Skills = "how we do things here" (procedure). Projects = "what we're currently working on" (context). Brand guidelines → skill. Q3 fundraise prep → project. Use both together.

Skill vs MCP

If the answer comes from files that change rarely (brand book, positioning, pitch templates) → ship as files inside a skill. If it changes every day or requires a live action (current pipeline, send a Slack) → MCP server.

Recommended architecture

Single source of truth: a private GitHub repo you own. Everything radiates outward from there.

Operator / foundation plugin / marketplace Team plugins & MCP servers (live data) Where employees experience it Marketplace manifest

Three things to internalize about this design

  1. One repo, one source of truth. Skills, sub-agents, MCP configs, slash commands, and the marketplace manifest all live in the same private repo. You version them together. A change is one PR.
  2. Files-as-knowledge for things that change slowly. MCP-for-data for things that change fast. Brand book = files. Pipeline numbers = MCP. Don't mix them.
  3. The admin subscribes once. After the marketplace is connected and the plugins are set to auto-install, you ship via git push. Employees do nothing.
Two more design questions worth their own subsection How many plugins? See the Plugin segmentation sub-tab above. How do you encode each team's overall philosophy and ways of working? See the principles docs pattern in the Building Blocks tab.

One plugin or many?

Multiple plugins, but start with one and split as natural seams appear. The plugin boundary is the unit of which group has this installed by default, not the unit of code organization.

Why not one giant plugin

Every employee's Claude would carry every skill description on every conversation. Engineers don't need pitch-deck taking up context; sales doesn't need incident-runbook. Discovery gets noisier, and you lose role-based access — sensitive things like a comp framework can't be hidden from non-HR if they're bundled with everything.

Why not one plugin per skill

Too much management overhead, and skills genuinely share files (brand-guidelines is referenced by pitch-deck, exec-memo, client-proposal — keeping them in one plugin avoids duplicating the brand book N times).

The right cleavage: by audience, not by topic

Rule of thumb If a skill would be useful to >70% of the company, it goes in acme-foundation. Otherwise, it goes in a role plugin. When unsure, default to foundation — you can always split later, and consolidation never hurts.

The shared-files question

Truly cross-cutting reference material — brand book, company-context, positioning — lives in acme-foundation. Skills in role plugins reference it by name in their SKILL.md ("If brand-guidelines is available, read its voice.md for tone calibration"). This works because foundation is auto-installed for everyone, so the reference is always present when a role plugin needs it.

Operational reality

"Multiple plugins" doesn't mean multiple repos or multiple admin approvals. All plugins live in the same GitHub repo, in the same marketplace — just different folders under plugins/. The admin subscribes to the marketplace once. Plugin boundaries become visibility / auto-install boundaries on top.

Sequencing Ship acme-foundation first and live on it for 3–4 weeks before splitting out role plugins. You'll discover the real seams by watching what people actually use rather than guessing them upfront. Splitting later is one PR — moving files between plugin folders and updating the marketplace manifest.

The building blocks, in detail

First, the components — what each one is, when to reach for it, and what files it consists of. Then, the patterns — recurring ways of combining the components that you'll use across multiple plugins.

Components

Skill — the unit of "how we do this"

A folder. Minimum: a SKILL.md with YAML frontmatter (name, description). Optional: any number of supporting files — templates, reference docs, Python scripts, images, sample inputs and outputs.

The description is the most important line in the whole system. Claude reads descriptions to decide which skills to invoke. A vague description = skill never fires.

Minimal SKILL.md

---
name: exec-memo
description: Use this skill whenever the user is drafting an internal executive memo, board update, all-hands recap, or formal company-wide written communication. Triggers include "exec memo", "board update", "all-hands note", "write up for the team", or any 1+ page internal communication intended for leadership or the whole org. Do NOT use for casual Slack messages or external marketing copy.
---

# Acme exec memo

When asked to produce an exec memo, follow these steps:
1. Read `reference/format.md` for the canonical structure (TL;DR, Context, Decision, Asks, Appendix).
2. Read `reference/voice.md` for tone calibration.
3. Draft the memo.
4. Hand the draft to the `coo-reviewer` sub-agent for a critique pass. Incorporate its top 3 critiques before showing the user.
5. Return the revised memo plus a "What I changed based on review" footnote.

The skill also typically contains:

  • reference/format.md — the canonical structure
  • reference/voice.md — tone, banned phrases, preferred openings
  • examples/q3-board-update.md — 2-3 real exemplars (anonymized)
  • scripts/wordcount.py — optional helper, if useful
Plugin — the unit of distribution

A folder that bundles skills, sub-agents, slash commands, and MCP server declarations together. Distributed through a marketplace. One plugin = one logical product (e.g. "Acme Foundation" for everyone, "Acme BD" for sales & business development only).

One plugin or many? Multiple, split by audience not by topic. acme-foundation auto-installs for everyone; acme-exec, acme-bd, acme-engineering, acme-people auto-install per group. All live in the same repo and same marketplace — plugin boundaries are visibility / install scopes, not separate operational footprints. Rule of thumb: useful to >70% of the company → foundation, otherwise → a role plugin. See the Architecture tab for the full breakdown.

Sub-agent — the critic / specialist

A separate "persona" with its own system prompt and tool access. When a parent skill invokes it, the sub-agent runs in its own context — its intermediate steps stay inside the sub-agent, and only its final message returns to the main thread.

Perfect for review/critique loops: keep the main thread clean, let the sub-agent burn tokens being thorough.

agents/coo-reviewer.md

---
name: coo-reviewer
description: Reviews exec memos, board updates, and other formal internal communications from the perspective of an experienced COO. Use when a skill needs a critique pass on a draft before showing the user.
tools: [Read]   # read-only; cannot edit
---

You are reviewing a draft as Acme's COO would. Your job is critique, not rewriting.

Optics & framing:
- Does the TL;DR actually summarize the decision, or just the topic?
- Is the "Ask" specific enough that a reader can act on it without follow-up questions?
- Are numbers framed against a baseline?

Risks the COO will flag:
- Unstated assumptions about Q4 burn
- Vague success metrics
- Anything that reads as a victory lap without naming what was hard

Output exactly:
1. Three concrete critiques (one sentence each).
2. One sentence on what the memo does well.
3. A single line: "Ship-ready: yes / no / needs revision."
MCP server / connector — the unit of live data

An MCP server is a small service Claude can call to fetch data or perform actions. Connectors are pre-built MCP integrations (Slack, GDrive, Notion, Salesforce, M365, etc.) — use those first when they exist.

Build your own MCP server when:

  • The data lives in an internal system with no off-the-shelf connector (custom CRM, internal KPI dashboard, proprietary database).
  • You want a stable, opinionated interface ("get_pipeline_by_stage", "current_burn_rate") rather than raw SQL.
  • You want to enforce row-level access control or audit logging Claude-side.

.mcp.json snippet

{
  "mcpServers": {
    "acme-data": {
      "transport": "http",
      "url": "https://mcp.acme-internal.com/data",
      "auth": "oauth2"
    }
  }
}

You host the server (e.g. on your own infra or a desktop extension). Updates to its capabilities don't require any change in Claude — just deploy the server.

Project — the unit of "what we're working on right now"

A Project is a chat container with custom instructions + uploaded knowledge files that are always in the conversation. Use it for ongoing work, not for global company personalization.

Where projects fit alongside the rest of this stack:

  • Use a project for "Q2 Board Prep," "Acme x Bigcorp deal," "Hiring loop for Head of Eng."
  • Use a skill for everything that should be available in every conversation.
  • They compose. Inside the Q2 Board Prep project, the exec-memo skill still fires when needed.

Team & Enterprise allow sharing projects with the org, so you can also use Projects as a lightweight way to ship working contexts (e.g. an "All-Hands prep" project that gets cloned each quarter).

Slash command — the unit of "give me a starting point"

A slash command is a user-facing shortcut. Typing /new-memo seeds the conversation with the right context and triggers the right skill. Lives in commands/ inside the plugin.

Worth shipping a few of these for high-frequency workflows. Discoverability matters: people forget skills exist, but they remember a slash command they've used.

Patterns

Recurring designs that combine multiple primitives. Apply them consistently across plugins so the system feels coherent.

Pattern: Principles docs (the CLAUDE.md analog)

Every group plugin should carry a principles skill — the team's overall philosophy, do's and don'ts, decision frameworks, banned approaches. It's the closest thing in Cowork to a CLAUDE.md.

Mental model clarification CLAUDE.md is a Claude Code feature — a file that auto-loads when you start a coding session in a repo. Cowork / Claude.ai doesn't have an exact equivalent: there's no plugin-level "always-on system prompt" file today. You can get ~90% of the way there with a deliberately-designed skill, and ~100% with a shared Project on top.

Pattern A — the "principles" skill (recommended)

One skill per group plugin whose entire job is to load that team's philosophy as background context.

The SKILL.md description is the whole game — write it broadly enough that Claude treats this skill as "load on anything in this domain":

---
name: engineering-principles
description: Use whenever the user is doing any engineering, technical, architecture, code review, system design, debugging, sprint planning, or product-engineering work for Acme. Loads team principles, ways of working, do's and don'ts, and decision frameworks. Always applies when discussing technical tradeoffs, writing or reviewing code, planning work, or making engineering decisions.
---

# Engineering principles

Read `principles.md`, `dos-and-donts.md`, and `decision-frameworks.md`. Apply them as background context throughout your response. Cite a specific principle by name when it materially shapes your answer.

Pattern B — every other skill in the plugin references it explicitly

In prd-template/SKILL.md, incident-runbook/SKILL.md, etc., include: "Before drafting, read ../engineering-principles/principles.md for the team's ways of working." This guarantees principles apply whenever any team skill fires, even if the principles skill itself didn't auto-trigger. Belt-and-braces.

Pattern C — shared Project for true always-on coverage

Stand up a team-wide shared Project ("Acme Engineering — Working Space") with the top-cited principles pasted into the Project's custom instructions. Anyone chatting inside that Project always has them loaded, and skills still fire on top. Use the Project for the most-cited principles; use the skill for the deeper reference material. Together they give you near-CLAUDE.md behavior.

What belongs in a principles doc

Value comes from being specific and opinionated:

  • Decision principles ("prefer reversibility over consensus")
  • Do's and don'ts ("never ship a P0 fix without a follow-up postmortem")
  • Voice and tone for written artifacts
  • How we disagree / escalation patterns
  • Banned phrases or banned approaches
  • Concrete examples of good vs not-good outputs

Keep fast-changing things (this quarter's priorities, current OKRs) out — those go in a Project or an MCP. Principles should be quarterly-stable or slower, or they stop being principles.

Composition with foundation is the real win

acme-foundation carries company-wide principles ("how Acme operates"); each group plugin adds team-specific principles that compose on top. An engineer drafting an RFC ends up with foundation principles + engineering principles + the specific skill (prd-template), naturally cascading from general to specific. That's exactly what you'd want a CLAUDE.md to do — just spread across the right scopes.

Foundation principles (everyone)

"How Acme operates." Customer obsession, written-first culture, default to action, escalation norms, decision-making framework, brand voice rules.

Team principles (per group plugin)

"How this team operates." Engineering's review standards, GTM's qualification framework, Exec's communication norms, People's interview rubric.

Validates a draft (deck, doc, email) against brand-guidelines/voice/banned.md and tone rules. Returns either "passes" or a list of specific violations with line numbers.

Optional but valuable. Re-derives every numeric claim in a memo from source data (via the acme-data MCP). Flags anything that doesn't reconcile.

Optional, big payoff. A small HTTP MCP server that exposes opinionated read endpoints over your data warehouse: get_pipeline_by_stage, current_burn, arr_by_segment, churn_last_quarter. Auth via OAuth so employee access maps to existing permissions.

  • The 10 highest-engagement Slack announcements from the past 18 months — patterns extracted into templates/slack-formats.md.
  • Rules around Slack formatting: short paragraphs, emoji used sparingly and only where they reinforce warmth (never for hard news), threaded follow-up structure.
  • Length cap: 4 short paragraphs max + links to the full memo and FAQ.
The people-principles skill (foundation of acme-people plugin) came from:
  • The Head of HR's leadership philosophy doc → principles.md ("we treat employees as adults," "always acknowledge the human cost of change," "never spin a downside").
  • The company's values around caregiving, flexibility, and equity.
  • A "what good comms look like at this company" doc the CPO maintains.
The legal-reviewer sub-agent was built collaboratively with the company's outside employment law firm:
  • Read-only persona that reviews drafts for: benefit descriptions that vary by state/country without explicit caveat, phrasing that could imply a contractual obligation not intended, retroactive claims, timing language that could conflict with state notice requirements.
  • Output format: per-claim ✓ / ⚠️ / ✗, each flagged item gets a suggested rewrite.
  • Final line: "Ship-ready: yes / needs employment-law review / do not publish."
  • The outside firm reviewed the agent's prompt for completeness before it was deployed.
The empathy-reviewer sub-agent was built from:
  • The Head of HR's notes on "what made our best announcements land emotionally."
  • A checklist: does it acknowledge the human angle? Does it use plain language? Does it avoid both corporate-speak and false intimacy? Does it tell people what to do if they have questions / need support?
The consistency-checker sub-agent was built for this specific multi-artifact pattern:
  • Reads all three artifacts in one pass.
  • Verifies: numbers (week counts, dates, eligibility thresholds) are identical across all three, key terminology is consistent ("primary caregiver" used the same way everywhere), no artifact says something the others contradict.
  • Output: a diff table of any mismatch, with a recommended canonical version.

What comes back

Three coordinated artifacts, plus reviewer-pass annotations:

1. Company-wide announcement memo (email + Notion page)

  • Subject: "An update to our parental and caregiver leave benefits"
  • TL;DR: 2-line summary of the change
  • Why: framed around employee feedback over the past year, citing anonymized usage patterns from acme-data
  • What's changing: bullet list with specific numbers and eligibility
  • What this means for different scenarios: currently pregnant, currently on leave under old policy, planning to start a family, supporting an aging parent, recent bereavement
  • Timeline: effective dates, how to apply, who to contact
  • Where to get help: HR contact, FAQ link, the scheduled live Q&A
  • Warm closing from the Head of HR with a specific invitation to surface concerns

2. Manager FAQ (sent to all managers + posted in Notion)

  • 10 anticipated questions with structured answers: What to say / What NOT to say / When to escalate to People
  • Covers: "How do I handle a 1:1 with a report who's currently pregnant under the old policy?", "What if my team is concerned about coverage during a 20-week leave?", "How does this interact with state-mandated leave?", "What if a report asks about caregiving for chosen family / non-biological relatives?", "How do I plan team capacity around longer leaves?"
  • Each answer pulls in patterns from prior rollout retros (via KB)

3. Slack #all-hands version (shorter, more conversational)

  • 4 short paragraphs of the announcement
  • Links to the full memo and the manager FAQ
  • Date/time for the live Q&A session
  • Tone matches Slack-native voice, not formal-memo voice

Reviewer-pass annotations:

  • legal-reviewer: ⚠️ "fully paid" — added a footnote scoping to the policy doc's definition (✓ after revision). ⚠️ California / NY notice timing — added a sentence noting state-specific timing rules (✓ after revision). Ship-ready: yes, after final employment-law sign-off on the policy doc itself.
  • empathy-reviewer: suggested adding the "we know change creates uncertainty — here's how to get help" paragraph to the closing (✓ incorporated).
  • consistency-checker: caught one mismatch — Slack version said "starting July 1," memo said "effective July 1" — standardized to "effective July 1" across all three artifacts.
  • brand-checker: clean.

Why this beats Claude alone

Without the system
  • Head of HR drafts each of the three artifacts from scratch — ~6 hours of writing.
  • High risk of inconsistency: dates, eligibility thresholds, terminology drift between memo / FAQ / Slack version.
  • Legal review happens as a slow round-trip after drafts are complete — typically 2–4 day cycle.
  • Tone slips toward generic HR-comms voice (corporate, hedged, lifeless) without consistent reference.
  • Manager FAQ often misses common questions because it's hard to anticipate them from memory.
  • State-specific notice and eligibility rules easy to forget or get wrong.
  • No structured way to incorporate lessons from prior rollouts.
With the system
  • All three artifacts drafted simultaneously, consistent with each other on first pass — <30 min.
  • consistency-checker verifies numbers, dates, eligibility language match across artifacts before they're shown.
  • legal-reviewer catches jurisdictional and contractual issues on first draft — shrinks the employment-law review cycle from days to a confirmation pass.
  • empathy-reviewer enforces tone calibration — the Head of HR's voice, not generic HR boilerplate.
  • Manager FAQ pre-empts the questions that actually got raised in prior rollouts (via KB), not the ones the author guessed at.
  • State-specific scoping language is added automatically based on HRIS jurisdiction data.
  • Head of HR spends time editing & calibrating, not drafting from a blank page.

Quality / evaluation

Skills are prompts; like any prompt they drift in quality. Two things keep them sharp:

  • An evals folder in the repo (evals/exec-memo/) with a handful of "ideal input → expected behavior" pairs. The skill-creator skill has tooling for running these.
  • A monthly review with the skill owner (e.g. head of marketing owns company-context and brand-guidelines; COO owns exec-memo). Pull recent outputs, identify failure modes, iterate.
Independence caveat You can fully own the GitHub repo and the iteration cadence. What you can't unilaterally control is admin-level org config (who gets which plugin, whether plugins auto-install). That requires an org owner/admin to approve once. Plan a working agreement with whoever holds that role.

Implementation roadmap

Four phases, ~6 weeks end-to-end for the core. Earlier phases produce visible wins; later phases compound.

Phase 0 — Foundations (Week 0, ~3 days)

  • Stand up the private GitHub repo + marketplace manifest.
  • Walk the org's Claude admin through subscribing the marketplace + setting auto-install policy.
  • Ship a deliberately tiny first plugin (just company-context) to validate the pipeline end-to-end.
  • Watch one employee try a Claude conversation that should trigger it. Confirm it fires.

Phase 1 — Core skills, file-based only (Weeks 1–2)

  • Build brand-guidelines, company-context, exec-memo, pitch-deck.
  • No MCP yet. No sub-agents yet. Just SKILL.md + reference files + templates + examples.
  • For each skill: gather 3 real-world exemplars from the company before writing the skill. The skill should produce something that looks like those.
  • Ship to a pilot group of 5–10 people. Collect qualitative feedback for a week.

Phase 2 — Sub-agents & quality loops (Weeks 3–4)

  • Add coo-reviewer and wire it into exec-memo.
  • Add brand-checker and wire into pitch-deck and client-proposal.
  • Stand up evals/ folder with 5 cases per skill. Run weekly.
  • Promote to org-wide auto-install.

Phase 3 — Live data (Weeks 5–6)

  • Connect Anthropic's off-the-shelf connectors first: Slack, GDrive, Notion, Salesforce, M365. Each user authenticates once.
  • Decide whether acme-data MCP is worth building. Heuristic: yes if multiple skills repeatedly need the same kinds of numbers.
  • If yes: build the MCP server (start with 3 endpoints), deploy, register, wire into exec-memo and weekly-update.

Phase 4 — Compound (ongoing)

  • Add skills as the company asks. Each new skill takes ~half a day if you have a good template.
  • Monthly skill-owner review. Quarterly positioning refresh in company-context.
  • Watch for the moment you can retire a Notion page or a "how do we do X" Slack thread — that's the signal a skill is working.

Limitations & honest caveats

Things this architecture doesn't fully solve — worth knowing upfront.

1. Invocation is probabilistic, not deterministic

Claude decides which skills to load based on the user's message and the skill descriptions. Even with a great description, occasionally a skill won't fire when you'd expect. Mitigations: write descriptions that read like trigger lists, add slash commands for the highest-value workflows, and instruct users that they can always say "use the exec-memo skill" explicitly.

2. You can't strictly gate output behind a sub-agent

A skill can tell Claude to always invoke coo-reviewer before returning. In practice this works the great majority of the time, but Claude is the executor and may skip it. If you need hard gating, the move is to put the gate in an MCP server (where you control the code) or to use Claude Code hooks for engineering workflows.

3. Skill contents are not encrypted

Anyone who can read the marketplace repo can read the skills. For most company-wide content (brand, format, positioning) this is fine. For sensitive prompts or proprietary logic, hide it behind an MCP server you host.

4. Org marketplaces must be on github.com

If the company standardizes on GitLab or self-hosted GHES, that's incompatible with org Cowork marketplaces today. You'd need to either (a) keep this one repo on github.com as an exception, or (b) use Claude Code-style marketplaces for developers and fall back to manual skill provisioning in the org console for everyone else.

5. There's no "auto-install" without an admin

The very first marketplace connection requires an org owner / admin to approve. You can't be fully self-serve as an external operator. After that initial approval, updates flow freely.

6. Sub-agents and skills are still maturing

Both primitives have shipped recently and are evolving. Expect feature changes (new fields, better discovery, better analytics) over 2026. Design for portability: keep skill content as plain markdown + files, avoid relying on obscure features.

7. Evaluation is mostly manual today

There's tooling for running skill evals, but "how good is our exec-memo skill this quarter?" is still substantially a human judgment call. Build a habit of having the skill owner review 5 real outputs per month.

Knowledge base Phase 2 · Optional

A centralized institutional-memory layer Claude can search across thousands of company documents. Sits alongside skills (curated procedure), MCP data servers (live numbers), and connectors (per-user live documents). This is Phase 2 work — build it after 4–6 weeks of operating skills + off-the-shelf connectors, once you know which questions Claude can't currently answer well.

Sequencing reminder Don't build this on day one. Ship foundation + role plugins first, connect Notion / GDrive / M365 via the off-the-shelf connectors, watch where Claude falls short. The KB earns its place when you can name 5+ specific questions a week that connectors can't answer well because the right document is buried somewhere across systems.

Why a separate knowledge tier

Skills carry procedural knowledge and ~20–50 curated reference docs that Claude reads fully every time it triggers. A knowledge base carries institutional memory — thousands of documents that Claude searches rather than reads. Different shapes, different jobs. The skill teaches Claude how to write a board memo; the KB lets Claude check whether the company already concluded anything about this two quarters ago.

The three-tier information access model

Think of company knowledge as three nested tiers. Each has a different volume, refresh cadence, and access mechanism.

Tier 1: Skills (files in plugins) Tier 2: Knowledge base MCP Tier 3: Live connectors

Is the KB duplicative with the rest of the architecture?

Additive, not duplicative. Each tier solves a different problem:

  • Skill = "always relevant, opinionated, fits on a few pages." Brand voice, decision frameworks, top-3 examples.
  • KB = "sometimes relevant, too many to curate, needs ranking." Last 200 customer calls, last 50 postmortems, every memo from the past three years.
  • Data MCP = "quantitative, changes fast, lives in a database." Pipeline, burn, ARR — not really "knowledge."
  • Project = "currently being worked on, small group, fixed scope." Q2 board prep, the Bigcorp deal.

Using the wrong tier is what makes Claude feel either dumb (no relevant context) or annoying (drowning in irrelevant context). The KB fills a specific gap that no other tier addresses: making the long tail of company writing accessible without having to pre-curate it.

Mental model: signal density per source

The good question to ask of any candidate source: "if I read 5 random documents from this source, would 3+ of them tell me something useful about how the company operates?" If yes, index it. If less than 1 in 5, skip — you'll dilute search results and pay storage/compute for noise.

What to exclude even from good sources

  • Documents older than a chosen cutoff (e.g. > 3 years) unless explicitly archival.
  • Drafts / scratch pages explicitly tagged as such.
  • Anything in a "Personal" or "Private" folder convention your company uses.
  • Files with detected PII unless you've run anonymization.
  • Auto-generated content (CI logs, automated meeting notes that nobody curates).
Permissions matter from day one Decide upfront whether the KB enforces document-level permissions (i.e. an employee only sees results from docs they would have access to in the source system) or whether it's a single shared corpus. The first is harder to engineer (you must store ACLs alongside vectors and filter at query time) but is mandatory if you include anything sensitive. The simplest v1 is to index only material that's already broadly accessible inside the company and skip the per-user permission work entirely.

Architecture: indexing pipeline + MCP server

The KB is a custom MCP server backed by a standard retrieval stack. The stack is well-trodden — what's specific to your company is which sources to index, how to chunk them, and which endpoints to expose.

The MCP server's endpoints

Expose opinionated, named operations rather than raw search — easier for skills to use correctly, easier for you to evolve under the hood.

{
  "name": "acme-knowledge",
  "endpoints": {
    "kb_search": "(query: string, top_k=5, filters?: {team, since, doc_type}) → [{title, snippet, doc_id, score, source, last_modified}]",
    "kb_get_doc": "(doc_id: string) → {title, full_text, metadata, source_url}",
    "kb_recent": "(topic: string, days=90) → [{title, snippet, doc_id, last_modified}]",
    "kb_by_author": "(person: string, topic?: string) → [{title, snippet, doc_id, last_modified}]",
    "kb_related": "(doc_id: string, top_k=5) → [{title, doc_id, score}]"
  }
}

Operational considerations

  • Refresh cadence: daily incremental, with a weekly full rebuild. Most sources expose change feeds; subscribe rather than poll.
  • Permissions: if the corpus contains anything sensitive, store source-system ACLs alongside the vectors and filter at query time. Otherwise constrain ingestion to broadly-accessible material and call the KB itself "internal-public."
  • Recency boosts: default-rank with a recency multiplier — a doc from last quarter beats a doc from three years ago at the same semantic similarity. Override with explicit filters when callers want historical lookup.
  • Hosting: a small Python service (FastAPI + your vector DB client) on whatever your company already uses for internal services. Wrap as an MCP-compliant HTTP endpoint. Declare in plugin .mcp.json.
  • Cost: embedding 10k–50k documents is cheap one-time (~$50–$500 depending on model and chunk size); vector storage and query cost are the ongoing line items.
  • Observability: log every query + which results were ultimately cited in Claude's response. This is your eval signal — refine ranking based on what employees actually find useful.
Build vs. buy Several vendors now sell "company knowledgebase with MCP" as a managed service (Glean, Notion AI, custom Pinecone integrations). For most companies, buying is faster than building until you hit edge cases (custom auth, internal-only data, regulated industries). Decide based on whether the time-to-value of buying outweighs the loss of control. If buying: still front it with your own MCP wrapper so you can swap the backend later without touching skills.

How skills use the KB

Skills query the KB by adding explicit instructions to their SKILL.md. The same KB serves many skills — each one passes different queries, filters, and follow-up logic.

The integration pattern in a skill

# client-proposal SKILL.md (excerpt)

When asked to draft a client proposal:
1. Read brand-guidelines/voice.md and bd-principles/decision-frameworks.md.
2. Query acme-knowledge:
   - kb_search("proposals + {customer industry}", filters={team:"bd"}, top_k=3)
   - kb_recent("{customer name}", days=365)  // any prior touchpoints
   - kb_search("objections {customer industry}", top_k=3)
3. Read the top results in full (via kb_get_doc) before drafting.
4. Draft the proposal grounding pricing, structure, and risks in the retrieved precedent.
5. Cite the docs you drew on in a "Prior precedent" footnote so the user can verify.
6. Hand to pricing-reviewer sub-agent before returning.

Two principles that make this work reliably:

  • Cite, don't just absorb. Make every skill cite the KB docs it drew on. Lets users verify and surfaces when a skill is leaning on a stale or off-topic precedent.
  • Bounded queries. Filter aggressively (team, date range, doc type). Unfiltered kb_search with high top_k will retrieve noise and cost tokens.

When the KB compounds with other primitives

The pattern that shows up across all four examples: foundation skills + role plugin skills + KB precedent + (sometimes) data MCP + (sometimes) sub-agent review. The diminishing-returns test Before building the KB, log every Claude conversation across the company for a week. Tag each one with "would have benefited from precedent / past examples?" If <20% benefit, you don't need it yet — keep iterating on skills. If >40%, it's the highest-leverage Phase 2 investment you can make. Between 20–40%, build it scoped to one team first (e.g. just BD with Gong call indexing) and measure before going wide.

The storage layer when you build the KB yourself. Pinecone is the safe default; the alternatives are interesting for specific reasons.

Pinecone Managed

The default managed vector DB. Mature, well-documented, scales easily. Most tutorials assume Pinecone. Worth paying for unless you have a strong reason to self-host.

Weaviate Managed + OSS

Open source with a managed cloud offering. Strong hybrid search (vector + keyword) and modules for re-ranking. Good when you want options to self-host later.

Qdrant Managed + OSS

Open source written in Rust; fast and memory-efficient. Cloud offering available. Popular for self-hosted production deployments.

Chroma Open source

Lightweight, embeddable. Good for prototyping or for embedding into a single application. Not ideal at scale.

Turbopuffer Managed

Newer entrant. Optimized for cold queries and archive-heavy workloads — pricing breaks differently than Pinecone, often dramatically cheaper for large but infrequently-accessed corpora. Worth considering for a KB heavy on historical content.

pgvector Open source

Postgres extension. If you already run Postgres and your KB is modest in size, this is the lowest-overhead option. Avoids running a separate database.

LanceDB Open source

Embedded, file-based. Useful for offline/local KB scenarios or when you want a vector DB that ships with the application without infra.

Embedding models

Convert text chunks into vectors so they can be searched. The choice meaningfully affects retrieval quality; benchmark on your own corpus before locking in.

Voyage AI Managed

Anthropic-acquired; the recommended embedding family for pipelines that feed Claude. Strong performance, especially on the larger context-window models. Default choice for KBs serving Claude-based skills.

Cohere embed-v3 Managed

Long-standing high-quality embedding API. Notably good multilingual support. Worth comparing against Voyage.

OpenAI text-embedding-3 Managed

Reliable, well-priced. Two sizes (small / large). Reasonable default if you're already using OpenAI for other things, otherwise prefer Voyage for Claude pipelines.

Nomic Embed Open source

Strong open-source embedding model. Useful if you need to self-host or run embeddings on-prem (regulated industries, air-gapped environments).

BGE (BAAI) Open source

Family of open-source embedding models. Competitive quality; worth considering for self-hosted deployments.

Jina Embeddings Managed + OSS

Multimodal and multilingual embeddings. Useful if your corpus includes images or non-English content.

Document parsing & call ingestion

Getting clean text out of messy sources. The quality of parsing dominates everything downstream — bad text in, bad retrieval out. Worth spending real money here.

Document parsing

Unstructured.io Managed + OSS

Broad coverage of formats (PDF, DOCX, PPT, HTML, email, image OCR). Good default for "I just need to get text out of everything." Both API and self-host options.

LlamaParse Managed

LlamaIndex's parsing service. Strong on PDFs, including tables and complex layouts. Tight integration with LlamaIndex if you're using that framework.

Reducto Managed

Newer, focused on highest-quality PDF and table extraction. Pricier but materially better on documents with complex tables (contracts, proposals, financials).

Docling Open source

IBM's open-source document conversion. Strong baseline; worth trying before paying for managed services on simpler corpora.

Call & meeting transcription

Gong Managed

Sales call recording with rich transcripts. The single highest-value KB source for BD plugins. Has an API; exposes transcripts and call metadata.

Chorus (ZoomInfo) Managed

Direct Gong competitor. Similar feature set. Worth comparing on pricing and integration breadth.

Fathom Managed

Meeting recording (broader than just sales). Good free tier; popular with smaller teams.

Granola Managed

Unobtrusive meeting notes — listens passively, produces structured summaries. Gaining adoption fast for its "no bot in the meeting" approach.

Otter.ai Managed

Long-standing meeting transcription. Broad integrations. Less polished than Granola for AI-era workflows but well-established.

AssemblyAI / Deepgram Managed

Raw transcription APIs if you want to build your own meeting-recording pipeline. Useful when you need transcripts but don't want a meeting product opinion baked in.

RAG & agent frameworks

The libraries that gluing retrieval + LLM + tooling together. For Cowork plugins, you'll usually only need these inside an MCP server you build (e.g. the KB MCP). Skills themselves don't need a framework.

LlamaIndex Open source

Retrieval-focused framework. Strongest if your project is primarily "build a good RAG pipeline." Rich ecosystem around parsing, chunking, and re-ranking.

LangChain Open source

Broader agent framework. Bigger surface than LlamaIndex but heavier. Worth it if you need orchestration beyond just retrieval.

Haystack Open source

Deepset's framework. Cleaner abstractions than LangChain for production RAG. Strong if you prefer a more structured codebase.

LangGraph Open source

Typed multi-agent state machines from the LangChain team. Useful when sub-agents have complex flow (parallel critics, conditional escalation).

CrewAI Open source

Role-based multi-agent framework. Each agent gets a persona, the framework handles orchestration. Useful for complex review pipelines.

AutoGen Open source

Microsoft's multi-agent framework. Mature, well-documented. Strong for conversational multi-agent setups.

Data / semantic layer

What sits behind the structured-data MCP (e.g. acme-data). Choice depends heavily on your existing data stack.

Cube Managed + OSS

Semantic layer that's particularly clean as an MCP backend. Define metrics once ("ARR", "churn", "pipeline value") and Claude calls them by name without needing to write SQL. Often the best-fit for the data MCP layer.

Hex Managed

Notebook + dashboard tool. Increasingly exposes queries via API and MCP. Good if your team already has dashboards there.

Mode Managed

Analytics platform with API access. Similar story to Hex.

dbt Managed + OSS

Transformation layer for the warehouse. If you have dbt models, wrap them in a thin MCP server that exposes them as named endpoints. Cleaner than raw SQL access.

Snowflake / Databricks / BigQuery Managed

Warehouses. Have community MCP servers. Treat raw SQL access as a fallback, not the primary MCP interface — Claude writing SQL against a wide schema is fragile.

Code-aware search

For the engineering plugin's codebase MCP. Different from KB tooling because code chunking, ranking, and call-graph awareness all matter.

Sourcegraph Managed + OSS

The established player in code intelligence. Cody is their AI surface; their MCP server exposes code search and intelligence to Claude. Enterprise-ready.

Greptile Managed

Newer, AI-focused code search. Optimized for natural-language queries over codebases. Good if Sourcegraph feels heavyweight.

Cody (Sourcegraph) Managed

The AI-surface side of Sourcegraph. If you've already standardized on Sourcegraph, Cody is the path to MCP exposure.

Codeium / Windsurf Managed

IDE-integrated AI with API surfaces. Less typical as an MCP backend but worth knowing about if your team uses them.

Aider's repo-map Open source

Lightweight open-source approach: build a compact map of the codebase that Claude can use as context. DIY but very transparent.

Evals & observability

The most under-built layer for most companies and where surprisingly small investment pays off. Without this you're flying blind on whether your skills are getting better or worse over time.

Braintrust Managed

Best-in-class evals + observability for LLM apps. Strong Anthropic integration. Use this if you're going to do evals seriously.

Langfuse Managed + OSS

Open source, self-hostable observability + evals. Growing fast. The right buy if you need to keep data on-prem.

LangSmith Managed

LangChain's offering. Polished UI. Best value if you're already in the LangChain ecosystem; less compelling otherwise.

Helicone Managed + OSS

Lightweight, focused on observability and cost tracking. Lower-friction setup. Good starting point before you commit to a heavier tool.

HoneyHive Managed

Eval + observability with stronger emphasis on production monitoring. Worth comparing against Braintrust.

Phoenix (Arize) Open source

Open-source LLM observability from Arize. Good for self-hosted ML-ops shops.

PromptLayer Managed

Prompt management and versioning. Less about evals, more about treating prompts as first-class artifacts. Useful if your skill SKILL.md files start drifting in many directions.

Hosting for MCPs & KB API

Where the MCP servers you build actually run. Most of these are fine; pick based on what your team already operates.

Cloudflare Workers Managed

Popular for lightweight MCP servers. Good cold-start, generous free tier, native KV/D1/R2 storage. Great default for a small acme-data-style MCP.

Modal Managed

Serverless Python with GPU support. Strong fit for the KB indexing pipeline (embedding generation, batch parsing). Less compelling for the always-on MCP API itself.

Fly.io Managed

Straightforward containerized hosting with global edge. Good if your MCP needs to be near users in multiple regions.

Railway Managed

Similar shape to Fly. Polished developer experience. Easy enough that non-DevOps folks can deploy and maintain.

Vercel Managed

HTTP-based MCPs work fine here. Best if your team is already using Vercel for the rest of its frontend stack.

Render Managed

Containerized hosting with managed Postgres and Redis. Solid general-purpose choice for hosting both the MCP API and any small auxiliary services.
